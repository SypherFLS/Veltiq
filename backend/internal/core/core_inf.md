Порядок, который обычно работает.

core/domain — импорт (статусы), чек в том виде, в каком он «истина» после парсинга. Пара строк, без фанатизма.
core/ports — минимум интерфейсов: сохранить/прочитать импорт, сохранить/списать чеки, парсер `Parse(...) -> []Receipt`. Без Postgres и без CSV в этих файлах.
core/service — один сценарий до конца осмысленного шага: «создать импорт -> вызвать парсер -> сохранить чеки -> пометить успех/ошибку». Логику статусов держать здесь.
Тесты на сервис с фейковыми реализациями портов (в памяти, заглушка парсера). Так проверяется ядро до базы и настоящего парсера.
infrastructure — подключить одну БД и реализовать те же порты (репозитории).
modules — один реальный парсер (один формат), который подходит под интерфейс из `ports`. Подставляется в `main`.
После этого цепочка живая: файл -> чеки в базе. Уже потом — ветка портов для базовой аналитики, Маркова и HTTP.

Дальнейший план действий:
1) Доделать `domain` (`Import`, `Receipt`, `Product`) и зафиксировать денежные поля в целых значениях.
2) Разбить большие интерфейсы в `ports` на узкие (`ImportStore`, `ReceiptStore`, `ReceiptParser`).
3) Реализовать первый `ImportService`-сценарий end-to-end.
4) Добавить 2-3 unit-теста на `ImportService`.
5) Подключить инфраструктурную реализацию портов и прогнать путь end-to-end.
# Core: понятный план от текущей точки

Ниже тот же удобный формат: коротко, по шагам, с приоритетами.

## Что уже сделано

- База структуры есть: `domain`, `ports`, `service`.
- В `domain` уже заведены `Import`, `Receipt`, `Metrics`, `Err`.
- По неймингу уже улучшено: `ID`, `CreatedAt`, `UnitPrice`, `Sum`, `CallReport`.

## Что делаем дальше (в порядке выполнения)

1. **Закрыть доменные модели (MVP)**
   - `Import`: `ID`, `TenantID`, `Status`, `ErrorCode`, `CreatedAt`, `UpdatedAt`.
   - `Receipt`: `ID`, `ImportID`, `TenantID`, `StoreID`, `PaymentType`, `Sum`, `Items`, `CreatedAt`.
   - `Product`: `Name`, `Quantity`, `UnitPrice`, `TotalPrice`.
   - Правило: деньги только целыми (`int`/`int64`), не `float`.

2. **Сузить и разделить порты**
   - Разбить большой интерфейс на отдельные:
     - `ImportStore` (создать/обновить/получить импорт),
     - `ReceiptStore` (сохранить/читать чеки),
     - `ReceiptParser` (распарсить сырьё в `[]Receipt`).
   - Убрать `...any` там, где можно дать конкретные сигнатуры.

3. **Реализовать первый сценарий в `ImportService`**
   - Старт импорта -> статус `processing`.
   - Вызов парсера.
   - Сохранение чеков.
   - Статус `done` или `failed` при ошибке.

4. **Добавить тесты на сервис**
   - 3 кейса минимум:
     - happy-path (всё прошло),
     - ошибка парсера,
     - ошибка записи чеков.
   - Использовать in-memory фейки портов.

5. **Подключить первую инфраструктуру**
   - Сначала in-memory или простая SQL-реализация.
   - `main` должен собрать сервис и запустить хотя бы один путь end-to-end.

6. **После этого подключать модули аналитики**
   - `BasicAnalytics` (sum/avg).
   - `MarkovAnalysis`.
   - `ReportService` как композитор готовых результатов.

## Критерии готовности ядра v1

- Есть рабочий сценарий: вход -> парсинг -> сохранение -> финальный статус.
- Весь поток проходит через `service`, а не напрямую через модули.
- Контракты в `ports` узкие и понятные.
- На `ImportService` есть тесты, покрывающие ошибки.

## Главное правило

Ядро отвечает за порядок и правила.  
Модули отвечают за вычисления и преобразования.  
Связка между ними только через интерфейсы и wiring в `main`.
# Core: текущий статус и что делать дальше

Этот файл отражает текущее состояние кода и простой план, как довести ядро до рабочего MVP.

## Что уже есть

- Есть базовые доменные файлы: `import.go`, `reciept.go`, `metrics.go`, `errors.go`.
- Есть заготовка портов: `ports/import_store.go`.
- Есть заготовки сервисов: `service/import_service.go`, `service/report_service.go`.

Это хороший старт: структура уже разделена на `domain/ports/service`.

## Что критично поправить в первую очередь

1. Привести нейминг к одному виду:
   - `reciept` -> `receipt`
   - `moduls` -> `modules`
   - `parcer` -> `parser`
   - `TenantdID` -> `TenantID`
2. Убрать `float64` для денег (`Receipt.Summ`) и перейти на `int64` в копейках.
3. Добавить защиту от деления на ноль в `Product.OneByTotal()`.
4. Сузить порты: убрать `data ...any` из `Read/Parse/Validate`, сделать явные сигнатуры.
5. Разнести ответственность:
   - `ImportModule` сейчас смешивает парсинг, валидацию, чтение и репортинг.
   - Нужно разделить хотя бы на 2-3 интерфейса (импорт/парсинг/репортинг).

## Минимальные доменные модели для MVP

### Import

- `ID string` (или `int`, если пока так проще, но желательно единообразно)
- `TenantID int`
- `Status ImportStatus` (`pending`, `processing`, `done`, `failed`)
- `ErrorCode string`
- `CreatedAt time.Time`
- `UpdatedAt time.Time`

### Receipt

- `ID`
- `ImportID`
- `TenantID`
- `StoreID`
- `PaymentType`
- `TotalAmount int64` (копейки)
- `Items []Product`
- `OccurredAt time.Time`

### Product

- `Name`
- `Quantity`
- `UnitPrice int64`
- `LineTotal int64`

## Какие порты сделать следующими

Вместо одного большого `ImportModule`:

- `ImportStore`:
  - `CreateImport(...)`
  - `UpdateStatus(...)`
  - `GetByID(...)`
- `ReceiptStore`:
  - `SaveBatch(importID, receipts)`
  - `ListByImportID(importID)`
- `ReceiptParser`:
  - `Parse(importID, raw) ([]domain.Receipt, error)`

Потом добавятся:

- `BasicAnalytics` (sum/avg)
- `MarkovAnalysis`
- `ReportComposer` (или сервис, который читает результаты и собирает ответ)

## Порядок работ от текущей точки

1. Привести нейминг и типы денег.
2. Доделать `domain` (Import + Receipt + Product).
3. Переписать `ports/import_store.go` на узкие интерфейсы.
4. Реализовать `ImportService` как один сценарий:
   - старт импорта
   - вызов парсера
   - сохранение чеков
   - обновление статуса
5. Написать 2-3 unit-теста на `ImportService` с in-memory фейками.
6. Подключить инфраструктуру (хотя бы in-memory, потом Postgres).
7. Добавить базовую аналитику и только потом Маркова.

## Главное правило

Ядро решает "в каком порядке и при каких условиях".  
Модули решают "как именно посчитать или распарсить".  
Связка модулей с ядром делается через интерфейсы и wiring в `main`.
